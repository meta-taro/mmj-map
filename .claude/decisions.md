# 決定と、その理由

新しい決定は**下に足す**。書き換えない。止めた決定は「止めた」と書いて残す。

各項目は 4 つで書く — **決めたこと / 根拠 / 採らなかった案とその理由 / これを止めるべき条件**。

---

## D-001 タイル生成パイプラインを自作しない（2026-09-14）

- **決めたこと**: ベースタイルは Protomaps の日次プラネットビルドから切り出す。
  OSM の生データからの変換パイプラインは書かない。
- **根拠**: そこを自作しても、**この企画の差分は 1 ミリも増えません**。
  差分があるのはスタイルと UI 部品の側で、パイプラインは既に解かれた問題です。
- **採らなかった案**: tilemaker / planetiler で自前変換する。
  → 数か月かかり、出来上がるのは既にあるものと同じです。
- **止めるべき条件**: Protomaps の日次ビルドが止まる、または利用条件が変わったとき。

## D-002 スタイルは生成物ではなく作品として扱う（2026-09-14）

- **決めたこと**: スタイル JSON は手書きし、リポジトリで追跡し、レビュー対象にする。
  ビルド生成物にしない。`.gitignore` で除外しない。
- **根拠**: **地図の美しさは、人が色を選んだ結果としてしか出ません。**
  生成物にした瞬間、この企画の唯一の差分が消えます。
- **採らなかった案**: 配色をアルゴリズムで振る。
  → それらしいものは出ますが、**それらしいものは既にあります**。
- **止めるべき条件**: 手書きの差分が汎用スタイルと見分けがつかない水準に留まるとき
  （そのときは企画ごと見直す）。

## D-003 地図サーバーを立てない（2026-09-14）

- **決めたこと**: 静的配信 ＋ HTTP Range で完結させる。
- **根拠**: **運用が増えないことが、この製品の価値の一部です。**
  地図を出したいだけの人に、サーバーを 1 台持たせない。
- **採らなかった案**: タイルサーバーを同梱する。
  → 「サーバーを立てなくてよい」という利点そのものを捨てることになります。
- **止めるべき条件**: 静的配信では成立しない要件（動的スタイル生成など）が
  主要な用途になったとき。

## D-004 最初のスプリントは新規実装ではなく切り出し（2026-09-14）

- **決めたこと**: 原案の Phase 1 / Phase 4 は書き起こさず、先行実装から切り出す。
- **根拠**: **同じものを二度書かないため。**先行実装は本番で稼働しており、
  踏むべき穴（Range 206・グリフの 404・分割アップロード）が既に判明しています。
- **採らなかった案**: 設計をゼロから引き直す。
  → 自由は増えますが、**既に分かっている失敗をもう一度踏みます**。
- **失うもの**: 初期構造に、先行実装側の都合（配信先の選び方・フレームワーク）が残ります。
  S2 で UI を書き直すときに剥がします。
- **止めるべき条件**: 切り出しが「固有の語を外す」では済まず、
  実質的に書き直しになると分かったとき（そのときは素直に書き直す）。

## D-005 タイル生成ワークフローだけは切り出さず書き直す（2026-09-14）

- **決めたこと**: 先行実装のローカル生成スクリプトは持ち込まない。
- **根拠**: **特定の PC のパス前提が残っており、再現可能ビルドの条件を満たしません。**
  「作った人がいなくなっても続くか」（PRD §0）に直接効く場所です。
- **採らなかった案**: 持ち込んでから直す。→ 動くものが手元にあると、直す動機が消えます。

## D-006 UI 部品は Web Components を軸にする（2026-09-14）

- **決めたこと**: Marker / Popup / Cluster は Web Components。React / Vue は薄いラッパ。
- **根拠**: フレームワークごとに本体を書くと、**3 つの実装がずれていきます**。
- **採らなかった案**: React 版を本体にする。
  → React を使わない利用者が最初から対象外になります。
- **止めるべき条件**: ラッパが薄くならず、結局フレームワークごとの実装が要ると判明したとき。

## D-007 ライセンスはコードが MIT、データが ODbL（2026-09-14）

- **決めたこと**: `LICENSE` は MIT 1 枚。データ側の条件は `LICENSES.md` に分けて書く。
- **根拠**: **スタイル JSON はデータではなく表現**なので ODbL の対象外です。
  一方でベースタイルは OSM 由来で ODbL。**混ぜて書くと、どちらも守られません。**
- **採らなかった案**: 全体を ODbL にする。
  → UI 部品まで ODbL になり、**採用の敷居が理由なく上がります**。
- **必ず守ること**: 画面から `© OpenStreetMap contributors` を消さない。

## D-008 費用削減を目的に掲げない（2026-09-14）

- **決めたこと**: 「地図の費用が下がる」を、この製品の目的にも成果にも書かない。
- **根拠**: 座標の取得元が「その提供者の地図の上に表示すること」を条件にしている場合、
  **ベース地図だけを差し替える自由はありません。**
  効く条件が限られるものを効果として約束すると、**採用した人が後で困ります。**
- **採らなかった案**: 訴求として使う。→ 一番伝わりやすい言葉ですが、正確ではありません。

## D-009 タイルビルドは Node で書く（シェルスクリプトにしない）（2026-09-15）

- **決めたこと**: `tools/tiles` を pnpm workspace の 1 パッケージとして Node + TypeScript で書く。
  `pmtiles` の呼び出しだけを子プロセスに出す。
- **根拠**: ベースルール §1 でこのリポの実行環境は既に Node（pnpm のみ）です。
  ビルド経路だけ POSIX シェルにすると、**Windows の開発機では手元で 1 行も走りません**（§3）。
  テストの道具もリポジトリ内で 2 系統になります。
- **採らなかった案**: `make build-japan` ＋ bash（原案 §20 の書き方）。
  → 読みやすいですが、bash の無い開発機で「手元で完結して起動・テストできる」を満たせません。
- **止めるべき条件**: タイル生成が Node から離れ、外部ツールの順次実行では足りなくなったとき。

## D-010 上流ビルドは pin し、自動では乗り換えない（2026-09-15）

- **決めたこと**: `tools/tiles/manifest.json` に上流ビルドを 1 個 pin する
  （key / size / md5sum / b3sum / basemap 版）。`pnpm tiles:resolve` が上流の索引と突き合わせ、
  **差があれば落ちる**。乗り換えは `--update` を人が打つ。
- **根拠**: 再現可能ビルドは「同じ入力から同じ出力」が言えることです。
  毎回「最新」を取りに行く形は、**同じコマンドが日によって違う地図を作る**ので再現可能ではありません。
  basemap のスキーマ版が変わるとスタイル側が壊れるため、**版が動いたことに気づける場所**も要ります。
- **採らなかった案**: 常に最新の日次ビルドを使う。
  → 追従は楽ですが、壊れたときに「いつの地図で壊れたか」を後から言えません。
- **これを止めるべき条件**: 上流が安定版（日付ではない固定 URL）を出し、
  そちらの方が中身の同一性を強く保証するようになったとき。
- **実行状況**: `20260915.pmtiles` / basemap 4.15.2 を pin。索引は
  `https://build-metadata.protomaps.dev/builds.json`（Protomaps の builds 画面が読んでいる先。
  **文書化された API ではない**ため、消えたら `resolve` が落ちて気づけるようにしてある）。

## D-011 点のまとめは MapLibre の source に任せ、件数は色ではなく大きさで表す（2026-09-17）

- **決めたこと**: `<mmj-cluster>` は GeoJSON source の `cluster: true` を設定して、
  排他の filter を持つ 3 枚のレイヤ（まとまり / 件数 / ばらの点）を足すだけにする。
  **まとめる計算を自分で書かない。**まとまりの大きさは `point_count` の step で 3 段階に変え、
  **色は件数によって変えない**。
- **根拠**: MapLibre の GeoJSON source は supercluster を内蔵していて、
  ズームごとの再計算まで持っています。同じものを外に書くと、**タイルではなく点の集計で
  地図が重くなる**場所を自分で作ることになります（PRD §3 の「厚くしない」）。
  件数を色の段階で表すのは**配色を決める行為**で、AI の領域ではありません（baseline §11）。
  大きさなら、後から人が配色を決めても壊れません。
- **採らなかった案**: 件数を色の段階（少ない=青 / 多い=赤）で表す。
  → MapLibre の例がこの形ですが、**赤がこの地図で何を意味するかを決めていません**。
  凡例のない色の段階は、読む人ごとに違う意味に読まれます。
- **既定の色について**: まとまりの色 `#3FB1CE` は **MapLibre の Marker が元から使っている値**、
  文字色 `#111418` は `styles/modern-dark.json` に既にある値です。**新しい色を足していません。**
  どちらも属性で差し替えられます。**これは承認された配色ではなく、
  DESIGN.md が埋まるまでの仮置きです。**
- **これを止めるべき条件**: 点が数万件を超えて source 側のクラスタリングが間に合わなくなったとき。
  そのときは点を**タイルにする**話であって、クラスタリングを自作する話にはなりません。
- **実行状況**: `packages/elements/src/cluster.js`（純粋関数・14 件のテスト）と
  `src/mmj-cluster.js`。実物は `docs/screenshots/2026-09-17-cluster-z11.jpg` /
  `-z15.jpg`（200 点の合成データ・大阪）。

## D-012 MVT は自前で読む。数えるためにライブラリを足さない（2026-09-17）

- **決めたこと**: `tools/tile-inspect` が MVT を自前でデコードする。
  `@mapbox/vector-tile` / `pbf` を依存に足さない。幾何は読まない。
- **根拠**: 用途は「何が何件あるか」を数えることだけで、形は読みません。
  形式は固まっていて、**属性まで読むなら 150 行**です。
  依存を足すと、その版と脆弱性を見続けることになります（baseline §12）。
  go-pmtiles は既に外部コマンドとして呼んでいるので、**新しい種類の依存を持ち込みません**。
- **採らなかった案**: `@mapbox/vector-tile` + `pbf` を入れる。
  → 幾何のデコードまで持っている分、**要らないものが増えます**。
  数えるだけのために、地図を描く能力を依存に持つ必要はありません。
- **これを止めるべき条件**: 幾何を読む用途が出たとき。
  座標の検証・面積の集計などを始めるなら、**自前で持つ理由はなくなります。**
- **実行状況**: `tools/tile-inspect`（13 テスト）。
  **本物のタイルに当てて、使い捨て実装と同じ数字が出ることを確認済み**
  （`15/28715/13016` の pois 516 件 → z15 で 45 件）。
  作っている途中で読み飛ばしの 1 バイトずれを出し、**合成タイルのテストをすり抜けた**。
  経緯は `docs/tiles/inspect.md` の末尾。

## D-013 全国の切り出しは bbox 1 個ではなく、四角の集合で行う（2026-09-17）

- **決めたこと**: `japan` の切り出しを、**倍率で 2 段に分けて `pmtiles merge` する。**
  - **z11 以上** … `--region`（`tools/tiles/regions/japan.geojson`・**8 つの四角**）
  - **z10 以下** … `--bbox`（四隅の全域）
  海岸線はなぞらない。**落としていないことは `test/coverage.test.ts` が機械で止める**（35 点）。
- **根拠**: 四隅（与那国島・沖ノ鳥島・南鳥島・択捉島）を 1 つの四角で囲うと、
  **太平洋をまるごと抱えます**。実測で **3.6 GB → 2.8 GB（-0.8 GB / -22%）**、
  タイル件数は **1,732,855 → 816,723（-53%）**。
  **遠方の島は 1 つも落としていません**（四隅を含む 35 点で確認）。
  件数の減りに対して容量の減りが小さいのは、**落ちたのが海のタイルで、中身が薄い**ためです。
- **採らなかった案**:
  - 海岸線の多角形を使う。→ **書いた人が読めなくなります。**四角 8 個なら
    「どこを含めたか」を人が目で確かめられます。精度を上げても、
    削れるのは残り 2.8 GB のうち海の薄いタイルぶんだけです。
  - 遠方の島を落として面積を減らす。→ **「日本の地図」ではなくなります**（manifest の note）。
  - `bbox` を manifest から消す。→ 残します。**この region が何を囲っているつもりか**を
    1 行で読めるようにしておくため。
- **やっていないこと**: **maxzoom は触っていません。**実測では
  z13 まで 622 MB / z14 まで 1.3 GB / z15 まで 2.8 GB で、
  **z15 だけで全体の 54%（1.5 GB）**です。**容量の本丸はここ**ですが、
  どこまで寄れる地図にするかは**品質の判断**なので、AI では決めません（baseline §11）。
- **これを止めるべき条件**: 四角を足しすぎて人が読めなくなったとき。
  そうなったら、素直に海岸線のデータを持つか、**容量を受け入れる**かの二択です。
- **実行状況**: **2026-09-17 に本番の切り出しを流し、`dist/tiles/japan.pmtiles` を差し替え済み。**
  `pmtiles verify` 通過。**2,790,049,315 バイト（2.60 GiB）/ タイル件数 819,672。**
  旧ファイルと**島 22 か所・低倍率タイル 3 枚をバイト単位で突き合わせ、全部一致**。
  実物は `docs/screenshots/2026-09-17-japan-z5-region.jpg` と
  `-todogasaki-z11.jpg`（region の境界に一番近い陸地）。

## D-014 pin は 1 本のまま。ただし確認済みの旧版を 3 本まで持ち、引数で戻れるようにする（2026-09-17）

- **決めたこと**:
  - `manifest.json` の `source.knownGood` に**確認済みの旧版を最大 3 本**持つ（新しい順）。
  - `pnpm tiles:extract -- <region> --build=previous`（`previous-2` / キー直指定も可）で切り出す。
  - **pin 以外で切ったら、出力名に版が入る**（`japan.20260914.pmtiles`）。
  - **manifest に無い版は使えない。**引数で任意の URL を取りに行かせない（baseline §21）。
  - 戻り先を足すのは `pnpm tiles:resolve --remember=<キー>`。**上流の索引と突き合わせてから書く。**
- **根拠**: D-010 で pin を 1 本にしたのは「同じコマンドが日によって違う地図を作らない」ためで、
  それは変えません。**ただし pin 1 本だと、戻り先がありません。**
  道も POI も上流で日々変わるので、**新しい版で何かが壊れたときに手で manifest を
  書き換えるしか手が無い**状態でした。それは急いでいるときに一番やりたくない作業です。
  上流（Protomaps）は **61 版・2 か月ぶんを保持**していることを実測で確認しました。
- **出力名に版を入れる理由**: 同じ名前へ上書きすると、**20 分かけて作った新しい方を
  古い版で潰す事故**が起きます。名前が違えば新旧を並べて見比べられます。
  配信へ出すときに rename が要りますが、**潰す事故よりは安い**。
- **採らなかった案**:
  - **pin を複数にする。** → どれが正か分からなくなります。pin は 1 本のままにします。
  - **どの版でも常に版名を付ける。** → 配信 URL が版ごとに変わります。
    CDN のキャッシュには有利ですが、**参照先を毎回書き換える**ことになります。
  - **引数で任意のキーを受ける。** → 任意の URL を取りに行かせることになります（§21）。
  - **戻り先を無制限に持つ。** → いつ確認したのか分からない版が溜まります。3 本まで。
- **これを止めるべき条件**: 3 本より前へ戻る必要が繰り返し出るとき。
  そのときは「戻り方」ではなく**上流に乗り換える判断の頻度**の問題です。
- **やっていないこと**: **切り出したファイルに「どの上流版から作ったか」を書いていません。**
  PMTiles のメタデータにあるのは OSM の時刻（`osmosisreplicationtime`）で、
  上流のキー（`20260915.pmtiles`）はどこにも入りません。
  いまは**ファイル名でしか区別できない**ので、pin で切ったものは名前からは分かりません。
  `pmtiles edit --metadata` で書けるはずですが、**まだ手を付けていません。**
- **実行状況**: 実装済み・**実際に戻して確認済み**（2026-09-17）。
  `pnpm tiles:extract -- kansai --build=previous` で `kansai.20260914.pmtiles` を作り、
  中身が別日であることを確認しました。

  | | OSM の時刻 | seq | 容量 |
  |---|---|---|---|
  | pin（20260915） | 2026-09-15T04:00:00Z | 122781 | 373,534,235 |
  | previous（20260914） | 2026-09-14T04:00:00Z | 122757 | 373,497,228 |

  知らない版（`--build=20200101`）は exit 2 で弾くことも確認済み。

## D-015 lint は oxlint。eslint は TypeScript 7 に追随していないため採らない（2026-09-17）

- **決めたこと**: 手元と CI の lint を **oxlint 1.83.0**（MIT）で回す。
  設定は `.oxlintrc.json`、入口は `pnpm lint`。**カテゴリは correctness / suspicious / perf の 3 つ**。
- **根拠**:
  1. **eslint + typescript-eslint はこのリポで使えない。** typescript-eslint 8.70.0 の
     peer は `typescript: >=4.8.4 <6.1.0` で、このリポの **TypeScript 7.0.2 が範囲外**。
     canary（8.70.1-alpha.22）まで見ても 7 系は入っていない。
     **eslint 単体では TS 構文を読む parser が無い**ため、逃げ道が無い。
  2. oxlint は **install script を持たず、runtime 依存も無い**。
     `onlyBuiltDependencies: []`（§1）と噛み合う。追加は 2 パッケージだけ
     （本体＋プラットフォーム別バイナリ）。
  3. peer に `oxlint-tsgolint >=7.0.2001` を持っており、**TS 7 / tsgo 前提で作られている**。
- **カテゴリを 3 つに絞った理由**（実測・59 ファイル）:

  | カテゴリ | 指摘 | 採否 |
  |---|---|---|
  | correctness | 0 | 採る |
  | suspicious | 12 | 採る |
  | perf | 5 | 採る |
  | pedantic | 95 | 採らない |
  | style | 1558 | 採らない |

  pedantic / style は**手書きのコードの書き方そのものを書き換える指摘**が大半。
  **赤が常態になったゲートは読まれなくなる**ので入れない。広げるときは、
  広げた結果を実際に直してから広げること。
- **切ったルールと理由**（`.oxlintrc.json` に同じ理由を書いてある）:
  - `eslint/no-await-in-loop` — 指摘 5 か所はすべて `tools/shot` の CDP 操作で、
    **直列でなければ壊れる**（起動待ちリトライ / ドメイン有効化の順序 / 描画の静止待ち）。
  - `unicorn/no-array-sort` — 指摘 8 か所を全部見て、**どれも自分が作った配列**だった。
    `toSorted()` へ書き換えても挙動は 1 件も変わらず、差分だけが残る。
- **severity を error にしてある**。oxlint の既定は warning で、**違反を報告しながら
  終了コード 0 を返す**（実測: 違反 2 件を報告して EXIT=0）。既定のまま置くと、
  赤が出ない lint が回り続ける。`tools/lint-gate` が**この 1 点をテストで縛っている**。
- **採らなかった案**:
  - **husky / lefthook** — hook のために依存を足す必要が無い。root の `prepare` で
    `core.hooksPath` を `.githooks` へ張れば済む。
  - **lint の対象にディレクトリを並べる**（`oxlint apps infra packages tools`）
    → **新しいパッケージが黙って漏れる。** 2026-09-17 の 1 日で `tools` が 3 つ増えており、
    実際に起きる事故。対象は `.` にして、除外は `ignorePatterns` 側に寄せた。

- **経路を計算しない根拠**: 計算には道路グラフとルーティングエンジンが要り、
  **D-003（地図サーバーを立てない）の外側**。作るのは外（ルーティング API でも AI でも）。
  **描く側に徹するのが「データを持たない。表現を持つ」**（D-001）の形そのもの。
  これを中に入れると、この製品は地図サーバーを持つことになる。
- **`setHTML` を使わない**: 媒体が登録した文字列をそのまま HTML として実行すると、
  `<img onerror=...>` の 1 行で、**その地図を置いたページ全体が乗っ取られる**。
  この製品は「媒体側が POI を登録する」使い方を想定している（D-011 の周辺）ので、
  **入ってくる文字列を信用しない**（baseline §21）。
  `popup.js` が中身を決め、`popup-dom.js` が `createElement` と `textContent` だけで組む。
  **文字が HTML として解釈される経路がそもそも存在しない。**
  `javascript:` と `data:` の画像は黙って落とす（`data:` は画像に見せかけた SVG から走る）。
- **採らなかった案**: `<mmj-step>` という要素を別に作る。
  → `<mmj-marker>` が既に lnglat ＋ 吹き出し ＋ 写真を持っている。**同じものを 2 つ作らない**。
  手で置く案内は `<mmj-marker>`、データで置く案内は `<mmj-route>` の点。
- **これを止めるべき条件**: **経路を計算してほしいという要望が繰り返し出たとき。**
  そのときに考えるのは「MMJ が計算する」ではなく、
  **「どのルーティング API と繋ぐ例を配るか」**のほう。D-003 を先に読むこと。
- **実行状況**: 部品・デモ（`apps/demo/route.html`）・説明書・データまで。
  実物で確認済み（線・案内 3 件・写真つき吹き出し・`<mmj-marker image>`）。
  **案内の見た目は既定の目印のまま**（番号も矢印も付けていない）。そこは `DESIGN.md` の領域。

## D-023 カバレッジを測り、80% を割ったら CI で止める（2026-09-21）

- **背景**: ECC `testing.md` は 80% を必須としているのに、**一度も測っていなかった**。
  CLAUDE.md の「ECC へ寄せたもの」にも「**いま測定すらしていないのが問題**」と書いてあった。
- **決めたこと**: ルートに `vitest.config.ts` を置き、`pnpm coverage` で
  ワークスペース 12 パッケージを 1 回で測る。**閾値 80% を CI に入れる。**
- **依存を 1 つだけ足した**: `@vitest/coverage-v8`（MIT・vitest 公式）。
  各パッケージへ入れると 12 個ぶん増えるので、**ルートに 1 つ**にした（baseline §1 / §12）。
  版は vitest と**完全一致で固定**（`^5.0.0` だと 5.0.1 を拾い、vitest が警告を出した）。
- **最初の実測（除外なし）**: statements 69.4% / branches 70.0% / functions 73.8% / lines 71.1%。
  **80% に届いていなかった。**
- **やったこと 1 つだけ**: `tools/serve/src/server.ts` が **34%** だった。
  `parseRangeHeader` のテストはあるのに、**206 を組み立てる本体が 1 行も通っていなかった**。
  本物のサーバーを起こして HTTP を投げるテストを足し、**90%** にした。
  **Range に 206 で応えられなければ地図は 1 枚も出ない**ので、ここは埋める価値があった。
- **測らないと決めたもの**（`exclude` に理由つきで明記）:
  - `**/src/cli.ts` `**/src/mcp.ts` `**/src/index.js` — 入口。引数の解釈は別ファイルへ出してある
  - `packages/elements/src/mmj-*.js` `popup-dom.js` — **要素は jsdom を入れず、
    ブラウザで撮って確かめる**（`attrs.js` の頭に理由）。判断が要る部分は純粋関数へ出してあり、
    そちらは 90% を超えている
  - `tools/style-check/src/snapshot.ts` — 上流から実測値を取り直す道具。
    **固定値に対するテストを書くと「上流が変わったこと」を隠す**
- **除外後**: statements 92.9% / branches 88.7% / functions 97.1% / lines 94.9%。
  **除外を入れて数字が上がったのは事実**なので、`exclude` には
  「**数字を上げるために除外を足さないこと。理由を書けないものは除外しない**」と書いた。
- **閾値が本当に落ちることを確かめた**: 一時的に 99% にして
  `ERROR: Coverage for lines (94.86%) does not meet global threshold (99%)` を見てから 80% へ戻した。
  **通るだけの検査にしない。**
- **採らなかった案**: jsdom を入れて要素も測る。
  → 依存が増えるうえに、**「実物をブラウザで見る」という設計を薄める**。
  0% のまま、理由を残すほうが正しい。
- **これを止めるべき条件**: **閾値を下げたくなったとき。**
  そのときに直すのは閾値ではなく、テストか除外の理由のほう。
- **実行状況**: 測定・閾値・CI への組み込みまで。`pnpm coverage` で誰でも再現できる。

## D-024 ラベルの言語は属性で切り替える。地域ごとにスタイルを増やさない（2026-09-21）

- **背景**: D-018 で地域を広げると決め、roadmap S5 に「その地域の `text-field` を持つスタイル
  （`name:zh` / `name:vi` …）」と書いていた。**そのまま作ると破綻する。**
  配色が 6 枚あるので、**地域 × 配色で 24 枚 48 枚と増える。**
- **決めたこと**: `<mmj-map lang="zh-Hant">` を足し、**読み込んだあとに `text-field` を差し替える**。
  スタイルは 6 枚のまま。色に対する `applyPalette` と同じ仕組み（`packages/elements/src/lang.js`）。
  あわせて `<mmj-map ideograph-fonts="...">` で漢字かなのフォントも差し替えられるようにした。
- **`name` への落とし先を残す**: その言語の名前が無い地物は、元の名前のまま出る。**消さない。**
- **上流のキーは実測した**（大阪のタイル・2026-09-21）:

      name:en 508 / name:zh-Hant 20 / name:zh-Hans 20 / name:ko 9 / name:vi 2

  **`name:zh` は存在しない。**`zh-Hans` / `zh-Hant` に分かれている。
  roadmap には `name:zh` と書いてあった。**推測で書いていた。**
- **当たらなければ投げる**: 言語を指定したのに元のままの地図を黙って出さない
  （`__TILES_URL__` が無いときと同じ扱い）。
- **採らなかった案**: 地域ごとにスタイルを複製して `text-field` だけ変える。
  → 6 枚の parity（D-019）を保てなくなり、**色を直すたびに全地域へ配る**ことになる。
- **実物で確かめたこと**: `lang="en"` は効いた（尼崎市→Amagasaki・東大阪市→Higashiosaka・
  JR難波→JR Namba）。**`lang="zh-Hant"` は大阪ではほとんど変わらない**（20 件しか無いため）。
- **台北で確かめ直した**（2026-09-22）: タイルを切り出して 3 言語を並べた。
  **台北市 → 臺北市 → Taipei** と切り替わる。
  台北のタイルには `name:zh-Hant` が **215 件**入っていた（大阪は 20 件）。
  **「効かない」のではなく「そのタイルに無かった」だけだった。**
  実物は `docs/screenshots/2026-09-22-taipei-lang.jpg`。
- **これを止めるべき条件**: **1 つの地図に複数言語を混ぜたくなったとき**
  （日本語の下に英語を小さく添える等）。それは `text-field` の差し替えでは足りず、
  スタイル側の設計の話になる。
- **実行状況**: 部品・説明書・地域プリセット 4 つ（taipei / shanghai / hochiminh / singapore）まで。
  **タイルはまだ切り出していない。**プリセットは bbox を書いただけで、実物は無い。
