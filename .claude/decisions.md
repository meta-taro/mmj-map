# 決定と、その理由

新しい決定は**下に足す**。書き換えない。止めた決定は「止めた」と書いて残す。

各項目は 4 つで書く — **決めたこと / 根拠 / 採らなかった案とその理由 / これを止めるべき条件**。

---

## D-001 タイル生成パイプラインを自作しない（2026-09-14）

- **決めたこと**: ベースタイルは Protomaps の日次プラネットビルドから切り出す。
  OSM の生データからの変換パイプラインは書かない。
- **根拠**: そこを自作しても、**この企画の差分は 1 ミリも増えません**。
  差分があるのはスタイルと UI 部品の側で、パイプラインは既に解かれた問題です。
- **採らなかった案**: tilemaker / planetiler で自前変換する。
  → 数か月かかり、出来上がるのは既にあるものと同じです。
- **止めるべき条件**: Protomaps の日次ビルドが止まる、または利用条件が変わったとき。

## D-002 スタイルは生成物ではなく作品として扱う（2026-09-14）

- **決めたこと**: スタイル JSON は手書きし、リポジトリで追跡し、レビュー対象にする。
  ビルド生成物にしない。`.gitignore` で除外しない。
- **根拠**: **地図の美しさは、人が色を選んだ結果としてしか出ません。**
  生成物にした瞬間、この企画の唯一の差分が消えます。
- **採らなかった案**: 配色をアルゴリズムで振る。
  → それらしいものは出ますが、**それらしいものは既にあります**。
- **止めるべき条件**: 手書きの差分が汎用スタイルと見分けがつかない水準に留まるとき
  （そのときは企画ごと見直す）。

## D-003 地図サーバーを立てない（2026-09-14）

- **決めたこと**: 静的配信 ＋ HTTP Range で完結させる。
- **根拠**: **運用が増えないことが、この製品の価値の一部です。**
  地図を出したいだけの人に、サーバーを 1 台持たせない。
- **採らなかった案**: タイルサーバーを同梱する。
  → 「サーバーを立てなくてよい」という利点そのものを捨てることになります。
- **止めるべき条件**: 静的配信では成立しない要件（動的スタイル生成など）が
  主要な用途になったとき。

## D-004 最初のスプリントは新規実装ではなく切り出し（2026-09-14）

- **決めたこと**: 原案の Phase 1 / Phase 4 は書き起こさず、先行実装から切り出す。
- **根拠**: **同じものを二度書かないため。**先行実装は本番で稼働しており、
  踏むべき穴（Range 206・グリフの 404・分割アップロード）が既に判明しています。
- **採らなかった案**: 設計をゼロから引き直す。
  → 自由は増えますが、**既に分かっている失敗をもう一度踏みます**。
- **失うもの**: 初期構造に、先行実装側の都合（配信先の選び方・フレームワーク）が残ります。
  S2 で UI を書き直すときに剥がします。
- **止めるべき条件**: 切り出しが「固有の語を外す」では済まず、
  実質的に書き直しになると分かったとき（そのときは素直に書き直す）。

## D-005 タイル生成ワークフローだけは切り出さず書き直す（2026-09-14）

- **決めたこと**: 先行実装のローカル生成スクリプトは持ち込まない。
- **根拠**: **特定の PC のパス前提が残っており、再現可能ビルドの条件を満たしません。**
  「作った人がいなくなっても続くか」（PRD §0）に直接効く場所です。
- **採らなかった案**: 持ち込んでから直す。→ 動くものが手元にあると、直す動機が消えます。

## D-006 UI 部品は Web Components を軸にする（2026-09-14）

- **決めたこと**: Marker / Popup / Cluster は Web Components。React / Vue は薄いラッパ。
- **根拠**: フレームワークごとに本体を書くと、**3 つの実装がずれていきます**。
- **採らなかった案**: React 版を本体にする。
  → React を使わない利用者が最初から対象外になります。
- **止めるべき条件**: ラッパが薄くならず、結局フレームワークごとの実装が要ると判明したとき。

## D-007 ライセンスはコードが MIT、データが ODbL（2026-09-14）

- **決めたこと**: `LICENSE` は MIT 1 枚。データ側の条件は `LICENSES.md` に分けて書く。
- **根拠**: **スタイル JSON はデータではなく表現**なので ODbL の対象外です。
  一方でベースタイルは OSM 由来で ODbL。**混ぜて書くと、どちらも守られません。**
- **採らなかった案**: 全体を ODbL にする。
  → UI 部品まで ODbL になり、**採用の敷居が理由なく上がります**。
- **必ず守ること**: 画面から `© OpenStreetMap contributors` を消さない。

## D-008 費用削減を目的に掲げない（2026-09-14）

- **決めたこと**: 「地図の費用が下がる」を、この製品の目的にも成果にも書かない。
- **根拠**: 座標の取得元が「その提供者の地図の上に表示すること」を条件にしている場合、
  **ベース地図だけを差し替える自由はありません。**
  効く条件が限られるものを効果として約束すると、**採用した人が後で困ります。**
- **採らなかった案**: 訴求として使う。→ 一番伝わりやすい言葉ですが、正確ではありません。

## D-009 タイルビルドは Node で書く（シェルスクリプトにしない）（2026-09-15）

- **決めたこと**: `tools/tiles` を pnpm workspace の 1 パッケージとして Node + TypeScript で書く。
  `pmtiles` の呼び出しだけを子プロセスに出す。
- **根拠**: ベースルール §1 でこのリポの実行環境は既に Node（pnpm のみ）です。
  ビルド経路だけ POSIX シェルにすると、**Windows の開発機では手元で 1 行も走りません**（§3）。
  テストの道具もリポジトリ内で 2 系統になります。
- **採らなかった案**: `make build-japan` ＋ bash（原案 §20 の書き方）。
  → 読みやすいですが、bash の無い開発機で「手元で完結して起動・テストできる」を満たせません。
- **止めるべき条件**: タイル生成が Node から離れ、外部ツールの順次実行では足りなくなったとき。

## D-010 上流ビルドは pin し、自動では乗り換えない（2026-09-15）

- **決めたこと**: `tools/tiles/manifest.json` に上流ビルドを 1 個 pin する
  （key / size / md5sum / b3sum / basemap 版）。`pnpm tiles:resolve` が上流の索引と突き合わせ、
  **差があれば落ちる**。乗り換えは `--update` を人が打つ。
- **根拠**: 再現可能ビルドは「同じ入力から同じ出力」が言えることです。
  毎回「最新」を取りに行く形は、**同じコマンドが日によって違う地図を作る**ので再現可能ではありません。
  basemap のスキーマ版が変わるとスタイル側が壊れるため、**版が動いたことに気づける場所**も要ります。
- **採らなかった案**: 常に最新の日次ビルドを使う。
  → 追従は楽ですが、壊れたときに「いつの地図で壊れたか」を後から言えません。
- **これを止めるべき条件**: 上流が安定版（日付ではない固定 URL）を出し、
  そちらの方が中身の同一性を強く保証するようになったとき。
- **実行状況**: `20260915.pmtiles` / basemap 4.15.2 を pin。索引は
  `https://build-metadata.protomaps.dev/builds.json`（Protomaps の builds 画面が読んでいる先。
  **文書化された API ではない**ため、消えたら `resolve` が落ちて気づけるようにしてある）。

## D-011 点のまとめは MapLibre の source に任せ、件数は色ではなく大きさで表す（2026-09-17）

- **決めたこと**: `<mmj-cluster>` は GeoJSON source の `cluster: true` を設定して、
  排他の filter を持つ 3 枚のレイヤ（まとまり / 件数 / ばらの点）を足すだけにする。
  **まとめる計算を自分で書かない。**まとまりの大きさは `point_count` の step で 3 段階に変え、
  **色は件数によって変えない**。
- **根拠**: MapLibre の GeoJSON source は supercluster を内蔵していて、
  ズームごとの再計算まで持っています。同じものを外に書くと、**タイルではなく点の集計で
  地図が重くなる**場所を自分で作ることになります（PRD §3 の「厚くしない」）。
  件数を色の段階で表すのは**配色を決める行為**で、AI の領域ではありません（baseline §11）。
  大きさなら、後から人が配色を決めても壊れません。
- **採らなかった案**: 件数を色の段階（少ない=青 / 多い=赤）で表す。
  → MapLibre の例がこの形ですが、**赤がこの地図で何を意味するかを決めていません**。
  凡例のない色の段階は、読む人ごとに違う意味に読まれます。
- **既定の色について**: まとまりの色 `#3FB1CE` は **MapLibre の Marker が元から使っている値**、
  文字色 `#111418` は `styles/modern-dark.json` に既にある値です。**新しい色を足していません。**
  どちらも属性で差し替えられます。**これは承認された配色ではなく、
  DESIGN.md が埋まるまでの仮置きです。**
- **これを止めるべき条件**: 点が数万件を超えて source 側のクラスタリングが間に合わなくなったとき。
  そのときは点を**タイルにする**話であって、クラスタリングを自作する話にはなりません。
- **実行状況**: `packages/elements/src/cluster.js`（純粋関数・14 件のテスト）と
  `src/mmj-cluster.js`。実物は `docs/screenshots/2026-09-17-cluster-z11.jpg` /
  `-z15.jpg`（200 点の合成データ・大阪）。

## D-012 MVT は自前で読む。数えるためにライブラリを足さない（2026-09-17）

- **決めたこと**: `tools/tile-inspect` が MVT を自前でデコードする。
  `@mapbox/vector-tile` / `pbf` を依存に足さない。幾何は読まない。
- **根拠**: 用途は「何が何件あるか」を数えることだけで、形は読みません。
  形式は固まっていて、**属性まで読むなら 150 行**です。
  依存を足すと、その版と脆弱性を見続けることになります（baseline §12）。
  go-pmtiles は既に外部コマンドとして呼んでいるので、**新しい種類の依存を持ち込みません**。
- **採らなかった案**: `@mapbox/vector-tile` + `pbf` を入れる。
  → 幾何のデコードまで持っている分、**要らないものが増えます**。
  数えるだけのために、地図を描く能力を依存に持つ必要はありません。
- **これを止めるべき条件**: 幾何を読む用途が出たとき。
  座標の検証・面積の集計などを始めるなら、**自前で持つ理由はなくなります。**
- **実行状況**: `tools/tile-inspect`（13 テスト）。
  **本物のタイルに当てて、使い捨て実装と同じ数字が出ることを確認済み**
  （`15/28715/13016` の pois 516 件 → z15 で 45 件）。
  作っている途中で読み飛ばしの 1 バイトずれを出し、**合成タイルのテストをすり抜けた**。
  経緯は `docs/tiles/inspect.md` の末尾。

## 未決

- **スタイルの 1 枚目をダークにするか、ライトにするか。**
  先行実装はダークから作られていますが、それはそのサイトの都合です。
- **npm パッケージの分け方**（スタイル / 部品 / タイル取得を別パッケージにするか）。
- **ベースタイルを誰がホストするか。** 自分でビルドする道は必ず残しますが、
  「すぐ試せる配信先」を用意するかどうかは未決です。
- **日本語グリフをどう出すか。** 調べた結果、**Protomaps が配っているフォントは
  Noto Sans の Latin だけで、CJK のフォントスタックがありません**
  （`protomaps/basemaps-assets/fonts` に Devanagari / Italic / Medium / Regular のみ）。
  つまり日本語ラベルは、こちらで用意しない限り必ず 404 になります。
  取れる道は 2 つで、**推すのは前者**です。
  - MapLibre の `localIdeographFontFamily` で漢字かなを閲覧側のフォントで描く。
    グリフ PBF を配らずに済み、S1 の「地図が 1 枚出る」に最短で届きます。
    代わりに字形が閲覧環境ごとに変わり、**組版を作品として作り込めません**（DESIGN.md §3 と衝突）。
  - Noto Sans JP（OFL）から glyph PBF を自前生成して配る。組版は握れますが、
    配信物が増え、**範囲が 1 つ欠けるだけで地図全体が真っ白になります**（PRD §4）。

  S1 は前者で通し、**S3 の組版の仕上げで後者へ移すかを決める**、を提案します。止めるなら S1 の間に。
