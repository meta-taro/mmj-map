## 決めたこと（提案）

### 1. POI は「出す kind を選ぶ」方式にする。除外リストにしない

`kind` は 30 種類以上あり、上流が増やせば黙って増えます。
**除外リスト方式だと、新しい kind が出た日に自販機が地図に並びます。**
出すものを列挙する方式なら、増えても静かなままです。

### 2. 4 つの群に分け、群ごとに出る倍率を変える

| 群 | kind | 出しはじめ | 意図 |
|---|---|---|---|
| **A. 目印** | stadium, museum, university, hospital, park | z13 | **街のどこにいるか**が分かる大物 |
| **B. 用がある場所** | post_office, school, library, police, pharmacy | z15 | 探して行く場所 |
| **C. 店** | supermarket, convenience, mall, doityourself, bank | z16 | 密度が上がるので遅らせる |
| **D. それ以外** | — | 出さない | |

**どの群も `min_zoom <= zoom` を併用します**（上流の判断を捨てない）。
群の倍率は「そこから出る資格を持つ」だけで、実際に出るかは上流の `min_zoom` 次第です。

この表なら、**京セラドームは z15 で出ます**（群 A は z13 からだが、
上流の `min_zoom` が 15 のため）。

### 3. `administrative` / `water` / `platform` は POI として出さない

二重になるか、地図に置く名前ではないためです（実測の項）。

### 4. 色とアイコンは決めない

群ごとに色を変える・アイコンを付けるのは **`DESIGN.md` の領域**です（baseline §11）。
この提案では**既存の `label-station` と同じ文字の扱いを流用**し、
大きさだけ群で変えることを想定しています。**AI は新しい色を作りません。**

### 5. 「育てる」は、上流へ書くことを第一にする

足りない POI を足す道は 3 つあり、**採るのは A と B、C は採りません**。

| 道 | 中身 | 判断 |
|---|---|---|
| **A. OSM へ直接書く** | 足りない POI を OSM に登録する。日次ビルドに自動で乗る | **第一選択** |
| **B. 自分たちのオーバーレイ** | ベースは Protomaps のまま、別 source を上に重ねる | **補助** |
| C. ベースタイルへ焼き込む | tilemaker 等で自前ビルド | **採らない** |

- **C を採らない理由**: `CLAUDE.md` の「データを持たない。表現を持つ」
  「タイル生成パイプラインを自作しない」に正面から反します。
  全国 3.6 GB を自前で作り直す運用が増えるのに、得られるものは A と B で足ります。
- **B はもう動いています。** `<mmj-cluster>`（D-011）が
  「GeoJSON を別 source で重ねる」仕組みそのものです。
  デモの合成 200 点を実データに差し替えれば、それが B です。

### 6. B で持つのは「判断」だけにする（ODbL の線引き）

**OSM 由来のデータを加工して配ると、ODbL の share-alike が働きます。**
名前・座標・属性をこちらのファイルへ写して配ると、そのファイルが ODbL の
対象になり、後から「このデータだけ別ライセンスで」が効かなくなります。

そこで、**自分たちが持つのは「OSM の id → 表示優先度」だけ**にすることを提案します。
名前と座標は上流のタイルから引きます。

```jsonc
// 持つのはこれだけ。名前も座標も書かない
{ "osm:n1234567890": { "rank": 1 }, "osm:w987654321": { "rank": 2 } }
```

**これが安全だと断言はできません。**「id の集合」が派生データベースに当たるかは
解釈が割れる論点です。**公開前に人が判断してください**（`LICENSES.md` の更新が要ります）。

> **2026-09-17 追記 — この回避策は、たぶん要りません。**
> 指摘を受けて考えを変えました。B で載せるものが「媒体の登録者が自分で入力した座標」なら、
> **そもそも OSM 由来ではない**ので share-alike の対象になりません。
> 上の「id → 優先度」は、OSM から写したものを配る場合の話です。
> 新しい形は [媒体が持ち込む POI](2026-09-17-media-poi.md) に分けて書きました。

### 7. OSM への書き込みは人がやる

アカウント・編集履歴・差し戻しの責任が伴います。
**AI はアカウントを使った編集を行いません。提案もしません**（baseline §13 / §14）。
AI ができるのは「この POI が OSM に無い」と**指摘するところまで**です。

## 採らなかった案とその理由

- **`pois` を丸ごと描いて、あとから間引く。**
  → z16 の時点で自販機 49 件・横断歩道 98 件が乗ります。
  間引きの条件を後から足す形は、**増えた kind に気づけません。**
- **群を作らず、`min_zoom` だけで出す。**
  → 上流の `min_zoom` は「その kind の中での重要度」で、
  **kind をまたいだ順位ではありません。**病院と自販機が同じ 16 で並びます。
- **`kind_detail` で細かく分ける。**
  → `stadium` の `kind_detail` が `baseball` であることに、
  いまの地図で意味がありません。**使い道が出てから足します。**
- **自前でベースタイルを作る（C）。**
  → 上記のとおり。**やるなら `.claude/decisions.md` の D-001 を覆す提案が先です**（§15）。

## これを止めるべき条件

- **群の分け方が「この地図で何を見せたいか」と合っていないとき。**
  これは設計判断で、決めるのは人です。群の数と中身はいくらでも動かせます。
- **z15 の実物を見て、45 件が多すぎるとき。**
  そのときは群 B・C の倍率を 1 つずつ遅らせます。
- **ODbL の線引き（項 6）が通らないとき。**
  通らないなら B は採れず、A だけになります。**それでも地図は成立します。**
