## 前提（違っていたら、この計画は組み直しになります）

- **利用予定の媒体が 2 件ある。** これがこの計画の性格を決めています。
  使う人がいる時点で、**壊れる変更のコストが自分たちだけの話でなくなります。**
- 2 件について、**まだ分かっていないことが 3 つあります**（末尾「人に聞くこと」）。
  この計画は「2 件とも自分でタイルをビルド・配信する」を仮に置いています。
  ここが違うと、0.2.0 と 0.1.0 の順序が入れ替わります。

## 決めたこと（提案）

1. **最初に出すのは中身ではなく経路。** `0.0.1` を空に近い形で publish する。
2. **0.x のあいだ、minor を壊れる変更に使う。** patch は修正のみ。
3. **パッケージは足並みを揃えて上げる**（lockstep）。0.x のうちは版を分けない。
4. **1.0.0 は日付で決めない。** 2 媒体が本番で動き、API が一定期間壊れていないこと。

### `0.0.1` — 経路を通す（これを最初にやる理由）

**中身を作ってから publish すると、経路の問題が一番まずい時に出ます。**

- **スコープ名は早い者勝ちで、取られたら変えられません。**
  2026-09-16 時点で `@mmj-map/{style,elements,tiles,react,vue}` は
  **5 つとも空いています**（registry が 404 を返す）。
  **空いていることは、押さえたことではありません。**
- publish の CI（トークン・権限・`access: public`・provenance）は、
  **最初の 1 回で必ずどこか詰まります。** 中身が無いうちに詰まらせておく。
- 2 媒体に `pnpm add` を 1 回試してもらえる。**入らないことが分かるのが早い。**

出すもの: `README` と `LICENSE` だけ。`0.1.0` で中身が入ると明記する。

## 版の運び方

- **0.x は minor が壊れる変更。** `0.2.0 → 0.3.0` で壊れてよい。patch は修正のみ。
- **足並みを揃える。** 4 パッケージの版を別々に動かすと、利用側が
  どの組み合わせで動くのか分からなくなります。0.x のうちは全部同じ版で出す。
- **`CHANGELOG.md` に壊れる変更を最初に書く。** 「何が壊れるか」を先頭に、
  移行手順を続けて書く。
- **publish は tag を打った時に CI が行う。** 手元から `pnpm publish` しない
  （どの木から出たのか分からなくなるため）。
- **npm のトークンは人が入れる**（§14）。AI は値を作らない・見ない。
- **provenance を付ける**（GitHub Actions の OIDC）。供給網の観点で、
  `minimumReleaseAge` を採っている方針と揃います。

## これを止めるべき条件

- **スコープ名が取れないなら、名前を決め直してから 0.0.1 を出す。**
  取られた後に変えると、2 媒体に 2 回入れ直させることになります。
- **`DESIGN.md` が埋まらないまま 0.1.0 を出さない。**
  AI が提案した色がそのまま既成事実になります（§11）。
- **2 媒体の要件が「部品まで要る」なら、0.1.0 の価値は小さい。**
  その場合は 0.4.0 までを 1 本のマイルストーンとして組み直す。

## 人に聞くこと

1. **2 媒体は、タイルを自分で配信しますか。**
   しないなら、配信先を誰が持つか（`decisions.md` 未決）が
   **第一ゴールの前提条件**になります。スタイルだけでは地図は出ません。
2. **2 媒体が要るのはスタイルだけですか、部品まで要りますか。**
   答えによって、第一ゴールが `0.1.0` か `0.4.0` かが変わります。
3. **いつ要りますか。** 逆算しないと、上の目安は絵に描いた餅です。
4. スコープ名 `@modern-map-japan` でよいですか。
   **調べた結果、5 つとも空いています**（2026-09-16）。取るなら早いほうがよい。
