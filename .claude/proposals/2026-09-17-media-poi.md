# 提案 — 利用者が自前の POI を持てるようにする（2026-09-17）

**これは提案です。決定ではありません。**

[POI の提案](2026-09-17-poi.md) の B（オーバーレイ）を、**MMJ が持つ機能**として書きます。

> **この提案は一度書きすぎました。** 窓口・仕分け・OSM への投稿手続きまで設計しましたが、
> **それは媒体側の運用であって、このライブラリが持つものではありません**（下の「範囲外」）。
> MMJ の仕事は「利用者が自前 POI を持てる形」を用意することだけです。

---

## 決めたこと（提案）

### 1. `<mmj-poi>` を足す。GeoJSON を渡すと、点と名前が出る

```html
<mmj-map tiles="..." style-url="...">
  <mmj-poi src="/data/our-poi.geojson"></mmj-poi>
</mmj-map>
```

`<mmj-cluster>` と同じく、**ベース地図には触らない**。別 source で上に重ねるだけ。
違いは**まとめないこと**で、数十件を 1 つずつ名前つきで出す用途に使う。

### 2. 名前をどの属性から取るかは、属性で指定できるようにする

既定は `name`。媒体ごとに `title` だったり `shop_name` だったりするため。
**MMJ 側で形式を決め打ちしない。**

### 3. 出しはじめの倍率を、利用者が決められるようにする

自前 POI が何件あるかは媒体によって違う。3 件なら z10 から出してよく、
3000 件なら z15 からにしたい。**MMJ は件数を知らないので、決めない。**

### 4. 色は決めない

`<mmj-cluster>` と同じ扱い。既定は MapLibre の既定値と
`styles/modern-dark.json` にある値を流用し、**新しい色を作らない**（baseline §11 / D-011）。

### 5. データは持たない

MMJ は GeoJSON を**読む側**であって、置き場所も更新も媒体のもの。
ジオコーダも持たない（住所→座標は媒体側の登録フローの仕事）。

---

## 権利（ODbL）について

**登録者が自分で入力した座標は OSM 由来ではない**ので、ODbL の share-alike は
かかりません。ベース地図（ODbL）と自前 POI（媒体のもの）は**別の層のまま**です。

ただし入力経路に条件が付きます。

- 他社の地図サービスから座標をコピーさせると、**その会社の規約の問題**になる
- OSM から写させると、**ODbL に戻る**
- **「自分の場所を、自分で地図上から指す」形**なら、どちらにも当たらない

権利のためだけでなく、**精度でもこれが一番良い**はずです。
店の位置を一番正確に知っているのは、その店です。

> 前の版で「OSM の id → 優先度だけ持つ」という回避策を書きましたが、
> **この形なら要りません。**取り下げます。

---

## 採らなかった案とその理由

- **MMJ が POI のデータベースを持つ。**
  → 「データを持たない。表現を持つ」（D-001）に反します。
  運用・審査・削除依頼・誤情報の責任を MMJ が抱えることになります。
- **`<mmj-cluster>` に「まとめない」オプションを足す。**
  → `clusterMaxZoom` を下げれば近いことはできますが、**名前を出す用途とは別物**です。
  まとめる部品に「まとめない設定」を足すと、両方の説明が複雑になります。
- **自前 POI をベースのスタイルへ差し込む。**
  → スタイルは作品であって、利用者のデータで書き換えるものではありません（D-002）。

## これを止めるべき条件

- **2 媒体が自前 POI を持っていないとき。** その場合これは将来の話です
- **`<mmj-cluster>` で足りるとき。** 点が多くて名前を出さない使い方なら、そちらで済みます

## 範囲外（このリポジトリで決めないこと）

以下は**媒体側 / 運営側の運用**です。MMJ は関与しません。
ただし一度設計したので、考えた形だけ残します（§24・消さずに残す）。

- **申し出を受ける窓口を持つかどうか。** 持つ場合、**拒む工程にしない**という指摘がありました。
  AI エージェントは可否ではなく**行き先**（OSM 向き / 自前 POI 向き / 保留）を出す。
  拒まない設計は放置が見えなくなるのと裏表なので、**保留の滞留が見えること**が条件（§29）
- **OSM への投稿。** まとまった数を入れる場合、OSM 側に import の手続きと、
  組織的な編集の申告に関する取り決めがあります。**運用開始前に最新の文書で確認が要ります**
  （この文書は記憶で書いており、実際に確認していません）
- **AI が OSM へ書かない**という線は、このリポでも守ります（baseline §13 / §14）
