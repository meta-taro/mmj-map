# 提案 — 梅田〜難波の「3 タイル」で、OSM から自分でベクター化して測る（2026-09-16）

**これは決定ではありません。**また、**D-001（タイル生成パイプラインを自作しない）を
覆す提案でもありません。** D-001 を**続けてよいかを測るための実験**です。

前提: [2026-09-16-umeda-namba.md](2026-09-16-umeda-namba.md)。
この 3 タイルは、そこで出した bbox の**内側に完全に収まります**（作業が無駄になりません）。

## 1. 「3 タイル」はどこか

z14 で数えると、**梅田と難波がちょうど 3 枚に収まります。**

| z/x/y | 覆う範囲 |
|---|---|
| `14/14358/6506` | 淀川の南 〜 大阪駅・梅田 |
| `14/14358/6507` | 中之島（堂島川・土佐堀川）〜 本町・船場 |
| `14/14358/6508` | 心斎橋・道頓堀 〜 難波 |

3 枚あわせて **経度 135.4834–135.5054 / 緯度 34.6561–34.7102**。
**約 2.0km × 6.0km。**縦 1 列に並んだ連続した 3 枚で、隙間がありません。

同じ範囲を z15 で見ると x=28716–28717 / y=13012–13017 の **12 枚**です。
**「範囲を決める単位」としては z14 の 3 枚、「絵として見る解像度」としては z15**、
と使い分けます。

> 数え方: `x = floor((lon+180)/360 × 2^z)` /
> `y = floor((1 − ln(tan φ + sec φ)/π)/2 × 2^z)`。
> この値は計算しただけで、**まだタイルを 1 枚も取得していません。**

## 2. なぜ「自分でベクター化」を試すのか

前回の提案で 1 つ未確認のまま残した問いがあります。

> **路線色を写すのに要る属性が、Protomaps のタイルに入っているのか。**

`DESIGN.md` は「鉄道の路線色は事業者が定めた色をそのまま使う。
パレットに合わせて振り直すと利用者は路線を読み違える」としています。
これを守れるかどうかは、**タイルの中に路線を識別できる何かが入っているか**で決まります。
入っていなければ、色を写したくても写す先がありません。

**この問いは、3 タイルあれば答えが出ます。**そして梅田〜難波は、
6 社 10 路線弱が重なる**日本で最も答えが出やすい 3 枚**です。

## 3. 測ること（実測して埋める。推測で書かない）

同じ 3 タイルを 2 通りで作り、**属性を突き合わせます。**

- **経路 A（いまの決定）**: Protomaps 日次ビルド → `pmtiles extract`
- **経路 B（実験）**: OSM 生データ → 自分で MVT 化

| # | 見るもの | なぜ要るか |
|---|---|---|
| 1 | 鉄道に `colour` / `ref` / `name` / `operator` / `network` が付くか | **路線色を写せるか。**この実験の主目的 |
| 2 | `name:ja` / `name:ja_kana` / `name:en` があるか | 「難波 / なんば / Namba」の出し分けができるか |
| 3 | 建物に `height` / `building:levels` があるか | 陰影・押し出しの可否（押し出しは推しません） |
| 4 | 地下鉄出入口・地下街（`railway=subway_entrance` 等） | **梅田の地下街は日本の地図の特徴。**汎用スタイルはまず持っていない |
| 5 | 道路の種別がどこまで分かれているか | 御堂筋を軸にした格子を 3 段で描けるか |
| 6 | タイル 1 枚あたりのサイズ | 取捨選択して軽くできる余地があるか |

結果は `docs/test-specs/` に TSV で置きます。**測れた欄だけ埋め、
判断の欄は空のまま残します**（ベースルール §19 — 合否は実物を見た人が書く）。

## 4. 答えによって、行き先が 3 つに分かれる

**ここが、この実験をやる本当の理由です。**「自作するか / しないか」の二択ではありません。

| 実測の結果 | 取る道 | 評価 |
|---|---|---|
| A に `ref` / `name` / `network` が入っている | **スタイル側に「路線 → 色」の対応表を持つだけ。**ジオメトリは 1 バイトも持たない | **最良。**CLAUDE.md の「データを持たない。表現を持つ」をそのまま満たす |
| A に識別子が無い／粗すぎる | ベースは A のまま、**鉄道だけを補助レイヤとして別に重ねる** | 次善。持つデータは日本の鉄道線のみで小さい。D-001 は生きたまま |
| A に鉄道がまともに入っていない | D-001 を見直す提案を、実測値つきで出す | **ここで初めて D-001 の話になります。**いまは違います |

**3 行目に落ちる可能性は高くないと思っています。**
それでも測るのは、1 行目か 2 行目かで**スタイルの書き方が変わる**からです。
測らずに書き始めると、後で全部書き直しになります。

## 5. どう作るか（経路 B の中身）

**この開発機は Windows で、WSL がありません。**道具選びはそこで決まります。

| 工程 | 採るもの | 理由 |
|---|---|---|
| OSM を取る | **Overpass API** で bbox 指定 → ディスクへキャッシュ | 追加のバイナリが要らない。3 タイル分だけなので 1 回で済む |
| GeoJSON → MVT | **`geojson-vt` ＋ `vt-pbf`**（どちらも純 JS） | Node だけで動く。**Windows で素で走る**（D-009 と同じ理由） |
| 置き場所 | `tools/osm-probe`（workspace の 1 パッケージ） | 名前で「探り」と分かる。**`tools/tiles` の本線には混ぜない** |

**採らなかった道具:**

- **tippecanoe** — 定番ですが C で、Windows 向けの公式ビルドがありません。
  WSL を前提にすると「手元で完結して起動・テストできる」（§3）を落とします。
- **planetiler** — Java が要り、**これは planet 規模の道具です。**
  3 タイルに持ち出すと、実験のつもりが自作パイプラインの着手になります。
  **D-001 が禁じているのは、まさにこの滑り出しです。**

**Overpass は共用の無料サーバーです。**1 回叩いたら結果をディスクに置き、
繰り返し叩きません。**CI からは叩きません**（走るたびに他人の資源を消費します）。

## 6. 権利について

OSM 生データも ODbL です。自分で MVT にしても条件は変わりません。
**`© OpenStreetMap contributors` の表示義務は、経路 A でも B でも同じです**（`LICENSES.md`）。
この実験によって新しい権利上の論点は増えません。

## 7. 採らなかった案とその理由

- **いきなり 45 タイル（前回提案の bbox 全体）で両方作る。**
  → 測りたいのは属性の有無で、面積は要りません。3 枚で同じ答えが出ます。
- **Protomaps のスキーマ文書を読んで済ませる。**
  → 文書に書いてあることと、**実際の日本のタイルに入っている値は別です。**
  日本の OSM でその属性が実際に埋まっているかは、文書では分かりません。
- **経路 B を作らず、A のタイルだけ中身を見る。**
  → 「A に無い」ことは分かりますが、**「OSM には有るのに A で落ちている」のか
  「OSM にも無い」のか**が区別できません。この 2 つは対処がまったく違います。

## 8. これを止めるべき条件

- **`tools/osm-probe` が 3 タイルを超えて育ち始めたら、そこで止めます。**
  ズームを増やす・範囲を広げる・レイヤを足す、が出てきたら
  **それは実験ではなく自作パイプラインです**（D-001）。
- 実験の結果が上の表の 1 行目（＝対応表だけで足りる）だったら、
  **`tools/osm-probe` は役目が終わりです。**結果を TSV に残して**消します**。
  残すと、使われないまま腐って「あるのに動かないもの」になります。
- Overpass が当該範囲を返せないほど重いなら、Geofabrik の近畿 pbf へ切り替えます
  （そのときは `osmium` が要るので、人に入れてもらう工程が 1 つ増えます）。
